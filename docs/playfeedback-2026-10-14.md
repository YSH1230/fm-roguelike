## 1. 판매 중 선수 규칙 (사용자 확정)

### 1.1 규칙
| 항목 | 규칙 |
|---|---|
| 등록 직후 | **화면 이동 없음.** `listForSale`의 `currentState.tab = 'draft'`·`draftSub = 'sell'` 자동 전환을 제거. 토스트(배너) "OOO 판매 등록 — 오퍼는 영입 탭의 판매에서 확인", 판매 탭 배지(오퍼 N건)는 유지 |
| 선발·벤치 | 판매 중 선수는 **선발·벤치에서 자동 제외**. 라인업은 대체 선수로 자동 재편(`pickBestXI`가 판매 중 선수를 풀에서 뺌). 수동 배치(manualOverrides·benchOverrides)에 있던 선수는 등록 때 그 칸을 비움 |
| 정원 N/22 | 판매 중 선수도 **정원에 포함** |
| 선수단 탭 | 판매 중 선수는 선발·벤치·예비 구역에서 빠져 맨 아래 "판매 중 N명" 구역(접힘 가능). 행: 이름·별·오퍼 N건·가장 빠른 만료 기한·[등록 취소] |
| 전력 | 전술 탭·팀 전력·시즌 전망·시뮬 모두 판매 중 선수를 **빼고** 계산(전력 손실이 생김) |
| 등록 취소 | 구역의 [등록 취소] 한 번으로 복귀. **복귀는 자동 배치**(pickBestXI가 별 기준으로 다시 계산, 예전 수동 배치는 복원하지 않음) |
| 수락 | 이미 라인업에서 빠져 있으므로 **공백 경고 없음.** 선수단에서 제거, 정원 −1, 거래 조직력 벌칙(충성형 추가 −2는 유지), 자금 +N |
| 만료·시장 종료 | 오퍼 전부 만료 또는 시장 종료 시 **조직력 −1**(`SALE_EXPIRE_CHEMISTRY`), 선수는 선수단으로 복귀(자동 배치), 알림 "OOO이(가) 선수단으로 돌아왔어요(조직력 −1)" |
| 시장 마지막 주 확인 | 판매 중 선수가 남은 채로 "다음 주"(전반기·후반기 시작)를 누르면 확인 줄 "판매 중 N명이 선수단으로 돌아와요(조직력 −N)" |
| 방출 확인 창 | 판매 중 선수의 [방출]·[판매 등록]은 비활성(먼저 등록 취소). 정원 초과 자동 방출(`capOverflow`)은 판매 중 선수를 제외(다른 후보가 없을 때만 포함) |
| 이중 등록 | 이미 판매 중이면 [판매 등록됨] 비활성(현행) |
| 이벤트·주장 | 판매 중 선수는 출전 요구 이벤트 후보와 자동 주장 후보에서 제외. 임명 주장은 유지(팔리면 이탈 규칙) |
| 오퍼 없는 선수 | "아직 오퍼가 없어요"로 구역에 남고 주마다 재시도(현행) |

### 1.2 등록 확인 문구(전력 손실 고지)
선수단 행 인라인 확인 줄(`confirmRelease`)을 아래로 교체한다.
- 기본: `OOO을(를) 판매 등록하면 선발·벤치에서 빠져요. 오퍼를 받는 동안 전력이 줄 수 있어요. [등록] [취소]`
- 선발인 선수: `…선발에서 빠져요. 대신 ○○○(포지션)이(가) 들어가요(전력 −N.N). [등록] [취소]` — 대체 선수와 전력 변화는 `pickBestXI` 미리보기로 계산(전력 변화는 별 차이가 아니라 팀 전력 숫자가 아닌 "전력 약간 감소/비슷/크게 감소" 3단계 문구로 충분: 변화 < 0.5 비슷, 0.5~2 약간, 2 이상 크게).
- 같은 포지션 대체가 없을 때: `…같은 포지션 선수가 없어 무명 보충 선수가 들어가요.`
- 판매 탭의 등록 안내 줄(`.note`)도 새 규칙으로 고친다: "판매 중인 선수는 선발·벤치에서 빠져요. 오퍼가 모두 만료되면 조직력이 조금 떨어지고 선수단으로 돌아와요."

### 1.3 수정 파일
`ui/app.mjs`(`listForSale`, `listPlayer`, `pickBestXI`와 그 호출처 전체(풀에서 판매 중 제외), `resolveListedSales`, `endListing`, `acceptSaleOffer`, `capOverflow`, 선수단 탭 렌더 `renderMarket`, `confirmRelease` 문구, 시장 마지막 주 "다음 주" 확인 `next-week-btn`), `ui/style.css`("판매 중" 구역, D), `tools/sim-v3.mjs`(판매 중 선수 제외 없음: 봇은 판매 즉시 처리하므로 변경 불필요).
- 구현 힌트: 판매 중 id 집합 `listedIds(currentState)`를 하나 만들어 `pickBestXI`의 `pool`에서 제외하면 호출처가 한꺼번에 해결된다. 자동 주장·출전 요구 후보 필터도 같은 함수를 쓴다.

### 1.4 테스트 기준
- 판매 등록 직후 현재 탭 유지(선수단 탭 → 선수단 탭).
- 선발 선수를 등록하면 `pickBestXI` 결과에 그 선수가 없고 정원 표시 N/22는 그대로.
- 등록 취소 후 같은 선수가 별 기준으로 다시 선발에 들어온다.
- 오퍼 수락 후 공백 경고가 뜨지 않는다(라인업이 이미 재편된 상태).
- 시장 종료 때 판매 중 선수는 모두 선수단으로 복귀하고 조직력이 정확히 −(선수 수).
- 판매 중 선수의 방출 버튼이 비활성이고, 정원 초과 자동 방출이 판매 중 선수를 먼저 건드리지 않는다.

### 6.4 전술 방향 효과 흡수
- 분산은 **②③ 토크의 톤으로 흡수**: risky → 공격, safe → 수비. **배수는 약하게: 공격 1.35 / 수비 0.6**(현행 1.6 / 0.45는 승점 분산이 커져 완주 시즌이 약 0.9 줄어듦, 8절). 이 배수에서 평균 변동성 배수는 (모험 4장×1.35 + 안정 3장×0.6)/7 = 1.03으로 무작위 선택 시 중립. 화면에는 기존 토크 카드의 "모험/안정" 라벨이 그대로 변동성을 알린다. ①④ 토크에는 변동성이 없다(균형).
- 상수: `DIRECTION_VARIANCE = { attack: 1.35, balance: 1, defense: 0.6 }`(또는 `TALK_VARIANCE`). 기대 승점은 그대로, 승점 분산만 달라진다(공격 ±27% / 균형 ±20% / 수비 ±12%).
- `runHalfSeason(..., direction, ...)` 인자를 유지하고 `currentState.direction`을 ②③에서 정한 값으로 채운다(기본 `'balance'`). 상수 이름을 `TALK_VARIANCE`로 바꿔도 된다.
- 성격 반응: ②③에도 `personalityReaction`을 적용(분위기 태그 pressure/warm/risk/stable), 시즌 합계 한도 −8~+8에 포함. 주장 대사: 기존 톤별 + 성격별 한 줄.
- 컷신: `showTalkPick` 재사용, 캡션 ② "전반기를 앞둔 라커룸", ③ "전반기가 끝난 라커룸 · {순위}위 · 승점 N". 디자인은 하프타임 변주 진행 가능(통지됨).

## 8. 시뮬 검증 (sim-v3 normal 봇, 각 N=500, 난수 시드 미고정)

| 구성 | 평균 완주 시즌(SE) | 1부 도달 | 1부 우승 | 5부 승점 sd |
|---|---|---|---|---|
| 현행 | 7.21 (0.19) | 20% | 23명(4.6%) | 16.7 |
| 부상 절반 + INJURY_POINTS 상향(4절) | 7.10 (0.18) | 20% | 15명(3.0%) | 15.6 |

| ②③ 신설, 숨은 방향 없음(균형) | 7.43 (0.18) | 21% | 16명(3.2%) | 15.6 |
| ②③ + 모험/안정 방향(공격 1.6 / 수비 0.45), ① 승점 유지(합계 ±4) | **6.37 (0.17)** | 18% | 15명(3.0%) | **18.2** |
| ②③ + 모험/안정 방향, ① 승점 제거 | 6.20 (0.15) | 18% | 8명(1.6%) | 18.2 |

- 부상 확률 절반(4절): 평균 완주 시즌이 같고(7.10 vs 7.21, 표준오차 안), 선발 잔부상·중간 부상의 시즌당 승점 손실도 −1.40 → −1.61로 비슷하다(INJURY_POINTS 상향이 승점 손실을 유지). **통과.**
- (폐기된 토크 안의 측정, 참고용) 토크 ②③ 신설만으로는 영향 없음(7.43). 1시즌부터 허용도 영향 없음(7.32).
- **문제:** 모험(risky = 공격 1.6배)/안정(safe = 수비 0.45배) 방향을 얹으면 완주 시즌이 **6.4로 약 0.9 감소**(표준오차 0.17의 5배, 유의미)하고 승점 분산이 16.7 → 18.2로 커진다. 원인: 풀이 모험 4장 : 안정 3장이라 무작위로 고르면 평균 변동성 배수가 (4×1.6 + 3×0.45)/7 = 1.11 > 1이고, 승점 분산이 커질수록 강등선 아래로 떨어질 확률이 늘어난다(봇은 라벨을 보지 않고 무작위로 고름).
- **해결(검증됨):** 변동성 배수를 모험 1.35 / 안정 0.6으로 약하게 하면(평균 1.03) 완주 시즌 7.02(SE 0.19), 1부 도달 23%, 1부 우승 20명(4.0%), 5부 승점 sd 16.8로 **현행(7.21)과 구분되지 않는다.** 6.4절·6.2절에 반영.

## 10. 튜토리얼 재설계: 스크립트형 별도 흐름 (사용자 확정 피드백, 2절을 대체)

문제: 지금 튜토리얼은 첫 진짜 런 위에 단계 0~15를 얹은 방식이라, "다음 주로"를 누르면 실제 주차 진행·시장 갱신·결산 시뮬이 돌아간다. 사용자 지시는 "튜토리얼은 본 게임에 아예 영향을 주지 않는다 + 읽고 누르는 대로 정해진 순서로 진행".

### 10.1 원칙
- 튜토리얼은 **고정 선수단·고정 영입 카드·고정 결과**로 진행하는 스크립트다. 본 게임의 난수(`Math.random`)·주차 진행·시장 갱신·시뮬에 의존하지 않는다.
- 사용자가 누르는 곳은 스포트라이트가 지정한 곳 하나뿐이다(나머지는 막힘). 탭 이동은 스크립트가 자동으로 해 준다(탭을 누르라고 시키지 않는다).
- 한 단계 = 한 가지 행동 + 한 가지 메시지. 시즌 중(튜토리얼 종료 후) 설명 팝업은 다시 나오지 않는다(3절 확정 유지).
- 종료 후 **구단 만들기부터 새 본 게임**(현재 `leaveTutorialRun`의 마무리 흐름 재사용 가능).

### 10.3 기술 방식 (프로그래밍 세션)
| 방식 | 내용 | 평가 |
|---|---|---|
| **A. 별도 모의 화면** | 튜토리얼 전용 정적 화면을 새로 만든다 | 격리는 쉽지만 화면이 이중으로 생겨 디자인과 어긋나고 유지비가 큼. 비추천 |
| **B. 고정 상태 + 기존 화면 재사용 + 가로채기 (추천)** | `buildTutorialState()`가 난수 없는 고정 상태를 만들고 기존 `renderMarket` 등을 그대로 그린다. 시간·난수가 필요한 7곳만 튜토리얼이면 스크립트 함수로 바꿔 부른다 | 화면이 실제와 같고, 본 게임 코드 변경은 분기 몇 줄 |
B의 구현 요령:
- 새 모듈 `ui/tutorial-script.mjs`: ① 고정 선수단(ids `t001…`, 별·태그·성격·부상 이력·리포트가 정해진 16명, 첫 선수에 특수 성향 1개), ② 고정 영입 카드 3장, ③ 고정 오퍼 2건, ④ 협상 고정 하한선, ⑤ 전반기 결과(고정 승점·순위·▲▼ 목록), ⑥ 단계 표(셀렉터·문구·허용 동작·다음 조건), ⑦ 훅 함수.
- `currentState.tutorial = true`(기존 `tutorialBackup`을 대체 또는 재사용). `startRun`을 거치지 않고 `currentState = buildTutorialState()`.
- 가로채기 지점(튜토리얼일 때 스크립트 함수로 분기): `nextWeek`(주차·시장·부상·이벤트 없이 고정 2주차 상태로 교체), 영입 카드 생성(`newShopOffer`·`generateScoutDelivery` 대신 고정 카드), 판매 오퍼(`rollSaleOffers` 대신 고정 오퍼), 협상(`openHaggle`의 `reserve`·`pat`을 고정값으로, 탐색·제안 로직은 그대로), `runFirstHalf`(고정 결과), 토크(`showTalkPick`의 고정 3장 모드, 이미 구현), 자동 저장(`persistRun` 건너뜀, 이미 구현).
- 본 게임 코드 영향 최소화: `if (currentState.tutorial) return tutorialHooks.X(...)` 분기를 위 7곳에만 둔다. 상태 필드는 본 게임과 같은 모양이라 렌더 코드는 그대로 쓴다.
- 입력 막기: 스포트라이트 오버레이가 항상 떠 있게(대상이 없는 구간은 투명 막)하고, 허용 대상만 클릭이 통과하게 한다(현행 `showSpot` 방식 유지).
- 종료: `leaveTutorialRun`의 마무리(`finish`: 상태 폐기, `resetPlayerIds`, `renderClubButtons`)를 재사용한다. 본 게임은 구단 만들기부터 새로 시작.
- records·저장·업적·flags(`tutorialStep` 제외)는 튜토리얼 중 갱신 금지(7절 유지).
- 건너뛰기: 어느 단계에서든 [건너뛰기] → 즉시 `finish`(인사·토크 없이).

### 10.6 테스트 기준
- 튜토리얼 중 `Math.random` 호출이 없다(난수 스텁으로 호출 시 오류를 내서 검증).
- 같은 클릭 순서로 100번 해도 화면(카드·승점·순위)이 같다.
- "다음 주로"를 눌러도 실제 주차 상태·`currentState.week`가 본 게임 값으로 쌓이지 않는다(튜토리얼 상태만 바뀜).
- 튜토리얼 후 `loadRecords().runs`·업적·저장이 변하지 않고, 구단 만들기에서 시작한 본 게임은 1주차 새 상태.
- 어느 단계에서든 [건너뛰기]가 새 구단 만들기로 이어진다.
